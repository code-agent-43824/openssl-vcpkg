# Журнал знаний

## 2026-10-17 — откуда DLL-сборка берёт провайдер `legacy`

- **Гипотеза.** В DLL-сборке `legacy.dll` не найдётся без явного пути: встроенный путь модулей
  указывает в `C:\Program Files\OpenSSL\bin`, а нашего файла там нет.
- **Что сделали.** Первая версия функционального теста загружала `legacy` без пути и только
  при неудаче пробовала папку exe. Потом по строкам внутри нашей `libcrypto-3-arm64.dll`
  проверили `MODULESDIR`, по исходникам OpenSSL 3.6.5 (`crypto/provider_core.c`,
  `crypto/defaults.c`) — как загружается модуль. Затем тест научили печатать, есть ли файл
  по встроенному пути, и из какого файла реально загружены `legacy.dll` и `libcrypto`.
- **Что показала проверка.** Без пути `legacy` загружался на всех DLL-вариантах. OpenSSL
  собирает полный путь из `MODULESDIR` (без `OSSL_WINCTX` реестр не читается) и грузит модуль
  по нему. На `windows-2025` и `windows-11-arm` файл
  `C:\Program Files\OpenSSL\bin\legacy.dll` есть: это OpenSSL, предустановленный на образе.
  Значит, проверка MD4 проходила на чужом модуле. С путём поиска, указывающим на папку exe,
  загружается наш `legacy.dll`; `libcrypto` в DLL-сборке — наша DLL рядом с exe, в статической —
  сам exe.
- **Вывод.** Гипотеза неверна, и опаснее, чем казалось: незаданный путь не даёт ошибку,
  а молча берёт чужой модуль. Тест теперь задаёт путь заранее и проверяет файл модуля;
  ловушка записана в `CLAUDE.md`.

## 2026-10-17 — линковщик не добавляет неиспользуемые DLL

- **Гипотеза.** Каждая тестовая программа DLL-сборки импортирует и `libcrypto`, и `libssl`.
- **Что показала проверка.** `functional.exe` импортирует только `libcrypto`: TLS он не
  вызывает, и линковщик не добавил `libssl`. Проверка `run.ps1` уронила все три DLL-варианта.
- **Вывод.** Линковку с DLL доказывает импорт `libcrypto`; требовать `libssl` можно только
  от программы, которая его вызывает.

## 2026-10-17 — что на самом деле лежит в статических библиотеках

- **Гипотеза.** Триплеты `-static` дают объектники, жёстко привязанные к статическому CRT:
  потребитель с `/MD` получит LNK2038. Так было записано в `CLAUDE.md` до первой сборки.
- **Что сделали.** Скачали артефакты run 1 на всех трёх архитектурах. Скриптом прочитали
  поле Machine у каждого объектника внутри `.lib` и поискали директивы `/DEFAULTLIB`.
  Ещё вытащили встроенную строку OpenSSL `compiler: ...`.
- **Что показала проверка.** Все объектники нужной архитектуры: x86 — 0x14c, x64 — 0x8664,
  arm64 — 0xaa64. Release собран с `/MT`, Debug — с `/MTd`, оба с `/Zl`. Директив
  `/DEFAULTLIB` нет ни одной: CRT в библиотеках не зашит. arm64 собран кросс-компилятором
  `Hostx64\arm64\cl.exe` из Visual Studio 18 на образе `windows-2025`. PDB нет, отладочная
  информация встроена (`/Z7`). Встроенный `OPENSSLDIR` — `C:\Program Files\Common Files\SSL`.
- **Вывод.** Гипотеза неверна: CRT выбирает компоновка потребителя. Чтобы не зависеть от DLL
  CRT, потребитель сам собирается с `/MT` / `/MTd`. `CLAUDE.md` исправлен.
